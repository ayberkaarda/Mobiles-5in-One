# Cost alerts and application caps

Security checklist item 22 (Harcama uyarısı kur). Patika is a portfolio project with no paid account behind it. The budget below is a planning sheet for a first production year at neighbourhood scale (a few thousand volunteers in one city). Prices are the providers' published list terms as understood at the time of writing; check them again at account setup. The application caps in the second half are implemented and cited from the code.

## Budget and alert thresholds

| Item | Provider (ADR-0002) | Planning budget | Alert at | Hard action at |
| --- | --- | --- | --- | --- |
| Hosting: API, Web, Worker containers + reverse proxy | One small VM or container host | 25 USD/month | 80% of the monthly budget (provider billing alert) | 100%: review instance sizes before scaling out |
| Managed PostgreSQL + PostGIS with PITR | Managed provider | 25 USD/month | DB size 70% of the plan's storage; connections 80% of the plan limit | 90% storage: grow the plan or prune (`idempotency_keys`, `email_tokens` are already pruned hourly) |
| Object storage (photos + backups) | Cloudflare R2 | 10 GB is in the free tier; 5 USD/month planned beyond it | 80% of 10 GB; Class A operations 80% of the free monthly allowance | Uploads are already capped per user per day (below) |
| Egress for photos | R2 (no egress fee) behind the CDN | 0 USD | CDN request volume 2x the 7-day average | Lower `Media:PhotoUrlMinutes` caching misses by setting `Storage:PublicBaseUrl` to the CDN |
| Transactional email | Resend | Free tier (3,000 emails/month, 100/day) | 70/day or 2,000/month; `cost.guard` alerts at 80% of each application budget | Two application budgets: `CostGuard:MaxEmailsPerDay` for non-critical kinds (default 5,000) pauses them; security mail has its own `CostGuard:MaxCriticalEmailsPerDay` (default 20,000; set it to the provider's daily limit, 100 on the free tier) and at that cap the API answers 503 `email_unavailable`; move to the paid plan |
| Push | Firebase Cloud Messaging | Free | `cost.guard` at 80% of each push budget | Non-critical cap (5,000/day) pauses them; the urgent budget (20,000/day, own counter) defers the rest of a fan-out to the next local day |
| Google Play | Play Console | 25 USD one-time registration; 15% service fee on Destekçi subscription revenue | n/a | n/a |
| Error reporting | None configured (no Sentry in the code) | 0 | n/a | n/a |

Alert routing: provider billing alerts go to the owner's email. The Worker's `cost.guard` and `backup.verify` jobs write a warning log line and mail the same count-only text to `Ops:AlertEmail` through the API's email transport (Resend; the Development folder sender locally). The alert mail bypasses the email budgets on purpose, so an alert about a cap is never stopped by it. `cost.guard` checks four budgets (non-critical pushes, urgent pushes, non-critical emails, security emails) every 5 minutes and alerts at most once per local day, budget and level: once at 80 percent and once at the cap (`CostAlertKind`, `CostAlertLevel`).

## What the cost guard does not cover

- Every user-facing kind today is security mail, so `CostGuard:MaxEmailsPerDay` only matters for kinds added later. When the security budget itself is used up (an attack that gets past the per-IP and per-address limits, or real volume), sign-up, resend, reset and deletion answer 503 until the next local day and the operator gets the `security emails` alerts at 80% and 100%; size it to the provider's daily limit.
- Forgot and resend send in the background after the pre-check. If the budget runs out in the moment between the pre-check and the send, that one request still answers 202 and the skip is logged as a warning; the same narrow window on `DELETE /me` keeps the deletion and logs an error. The per-recipient limit is not part of the pre-check (it would tell known and unknown addresses apart), so a recipient over 10 security mails a day gets 202 without a new code on forgot and resend, as with the existing cap of 10 codes per day.
- A deferred urgent fan-out resumes by position in the nearest-first order (`fanout_offset`): devices registered or removed in between can shift that order, so a few devices may be skipped or notified twice. The 500-device total per post still holds.
- The alert line is `cost.guard: {Budget} at {Used} of {Cap} on {Day} ({Level}); {Effect}` (`CostAlertNotifier`, `PushCostGuard.cs`); the API also logs `cost.guard: {Channel} daily cap {Cap} reached on {Day}; a message of kind {Kind} was not sent` for each skipped send. No recipient, subject or body is ever logged or mailed.
- The "alerted today" state is per Worker process (`CostGuardAlertState`), so a restart can alert twice on one day. With one Worker instance (ADR-0002) that is acceptable.
- Rate limits are in memory per API instance. Running more than one instance needs the shared store from ADR-0002.
