# ADR-0006: Mobile app core

- Status: Accepted
- Date: 2026-10-25

## Context

The MAUI Android client (`app/Patika.App`) needs one shared foundation before the map, animal, urgent and account screens are built in parallel: a typed API client with token refresh, Turkish error messages, an offline map cache, an outbox for records made without a connection, foreground location, navigation and a view-model base. Volunteers feed stations in courtyards and parks with poor coverage, so a "Beslendi" tap must never be lost or counted twice. Refresh tokens rotate and the API revokes the whole family when one is reused, so two parallel refreshes would sign the user out. ADR-0004 requires a justification for every runtime package the app adds.

## Decision

- Split the client into `app/Patika.App.Core` (plain `net10.0` class library) and `app/Patika.App` (`net10.0-android`). Core holds everything that does not need MAUI: `Api/` (client, `TokenManager`, error mapping), `Offline/` (SQLite database, map cache, outbox, replayer, field actions), `Location/` and `Navigation/` interfaces, and `Mvvm/ViewModelBase`. The app holds the platform adapters (SecureStorage token store, `Connectivity`, `Geolocation`/`Permissions`, Shell navigation), pages and view models. `tests/Patika.App.Tests` tests Core on `net10.0` without an emulator. Core references `src/Patika.Contracts` for DTOs instead of copying them.
- API client: one `HttpClient` with the base URL from embedded `appsettings.json` (`appsettings.Development.json`, Debug only, points at `http://10.0.2.2:5000/`). The production value `https://api.patika.app/` is a placeholder until the API host is fixed. Problem details map to `ApiException` with a Turkish message chosen by `code`, falling back to the HTTP status; server titles are never shown. Every POST sends an `Idempotency-Key` (a fresh UUID, or the outbox item's stable key). Bodies are the Contracts records of the phase 3 API (the API rejects unknown JSON members): verification sends the six-digit code as `{email, code}`, replayed records send `clientCreatedAt`. There is no fallback for older API shapes, so a 400 is a final answer and the body never changes under one key.
- Tokens: the access token lives in memory only; the refresh token and account id live in SecureStorage. Refresh is single-flight: concurrent callers share one exchange, and a caller holding a token that another caller already replaced gets the new token without a second exchange. Every session boundary (sign-in, sign-out, expiry) moves a session generation; memory and storage writes and the generation check before them run under one async lock, so a refresh that finishes after a sign-out or an account switch is discarded. A refreshed request that still gets 401, or a rejected refresh token, wipes both tokens (only if that session is still current) and routes to sign-in. Sign-out revokes the refresh token when online, wipes local tokens, then awaits the wipe of the outbox and the map cache before it returns.
- Offline storage: `Microsoft.Data.Sqlite` over one file in the app's private folder. Tables: the last map region (one slot), station details (at most 300, at most 7 days old, evicted on every save) and the outbox. No user position and no token is stored. A viewport derived from the user's location is never saved; browsed viewports are widened to a 0.01 degree grid before saving. Cache writers pass the cache epoch they read before fetching; a wipe moves the epoch, so late responses cannot write wiped data back. Android backup stays off.
- Outbox: Beslendi, Mama bitti and Bugün gördüm always go through the outbox, online or not, so there is one path. Each item keeps its Idempotency-Key and client time from the moment of the tap. Replay is strictly oldest first per account; a transient failure (no connection, 5xx, 408, 429, `idempotency_in_progress`) stops the run and backs off 5 s doubling to 15 min, so a later record never overtakes an earlier one; a final 4xx (for example `feeding_cooldown`) is kept as rejected and the run continues. A record that cannot be read, or that fails transiently 20 times or is older than 7 days at a failure, becomes failed and stops blocking the queue; rejected and failed records stay visible with their reason until the user dismisses them. A pass is bound to one account and session: it reads only that owner's items, any session change cancels it, and the client sends a bound request only with a token of that session, so a record can never go out under another account. Runs never overlap. Triggers: start-up, sign-in, connectivity returning, a new item, the backoff timer. Signing in as another account drops what the previous one left.
- Location: foreground (`ACCESS_FINE_LOCATION`/`COARSE`, "while using the app") only, no background permission. The app shows its own rationale before the system prompt and reports "blocked" when Android stops asking. A fix is returned to the caller and never stored, logged or sent by the service.
- Cleartext HTTP to `10.0.2.2` (the emulator's host alias) exists only in Debug builds: the csproj swaps in `Platforms/Android/DebugResources/xml/network_security_config.xml`; the Release config allows no cleartext at all.
- Navigation: every canvas screen has a route in `Core/Navigation/Routes`; packages B, C and D replace the placeholder page registered for their routes.

Runtime packages (both are pinned in `Directory.Packages.props` and listed by ADR-0004 or added here):

- `CommunityToolkit.Mvvm` 8.4.2: approved in ADR-0004. Compile-time source generators write the `INotifyPropertyChanged` and command code; no runtime reflection, no data access, MIT, .NET Foundation.
- `Microsoft.Data.Sqlite` 10.0.13: Microsoft's ADO.NET provider, MIT, released with .NET. It brings `SQLitePCLRaw.bundle_e_sqlite3` 2.1.x (Apache-2.0, maintained by SourceGear, the same native SQLite build EF Core uses on Android). Chosen over `sqlite-net-pcl` because it is first-party, needs no ORM attributes on Contracts types, and runs unchanged in the `net10.0` tests. Alternatives considered: `sqlite-net-pcl` (third-party ORM, same native library), Preferences/JSON files (no transactions, no ordering guarantees for the outbox). Data access: one local file in the app sandbox, no network. Updates follow the .NET servicing train with the other `10.0.x` pins.

## Consequences

Feature packages build on tested services: they inject `PatikaApiClient`, `FieldActions`, `MapCache`, `ILocationService` and `INavigationService` and derive view models from `ViewModelBase`. Core logic is covered by `Patika.App.Tests` (token single-flight, expiry and late-refresh discard, error mapping, idempotency keys, outbox ordering, backoff, attempt and age limits, account isolation, duplicate suppression, cache eviction and wipe races) without an emulator; platform adapters are exercised only on a device. Exactly-once delivery of replayed records relies on the API honouring `Idempotency-Key`. The API accepts `clientCreatedAt` only up to 72 hours old, so a record kept offline longer is refused and shown as rejected. The placeholder production URL must be replaced before a release build. The native SQLite library (`libe_sqlite3.so`) ships once per ABI in the APK.
