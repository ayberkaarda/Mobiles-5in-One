# Askıda — Security Verification Matrix

|                |                                                                                                                                                                                                                                                                                                                          |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Scope          | The 23 items of product spec section 6. One row per item: status, the proof that exists, and the proof that is still missing.                                                                                                                                                                                            |
| Moment         | **Phase 0 skeleton.** No Askıda server, app or test exists yet, so almost every row is `not-started`. The matrix is kept up to date at every phase gate and finalised in Phase 6.                                                                                                                                        |
| Rule           | Evidence names only files, workflows and commands that exist in the repository at the time of writing. An item is `done` only when its spec **Verify** proof exists, passed in a recorded run, and does not depend on an external system that cannot be exercised here. A planned proof is never listed as evidence.     |
| Statuses       | `done` — implemented for every endpoint and component that exists, with a passing test or an existing document as proof. `partial` — some implementation or proof exists; the exact missing proof is named. `not-started` — no implementation or proof yet (a draft document alone does not count as a control).         |
| Evidence limit | Some proofs depend on systems this project cannot reach (a payment provider account, mobile store accounts, macOS, real devices). Where that applies the row says `not exercised: <reason>` and its status cannot be `done`. The full list of limits and the reasoning are in `../adr/0006-portfolio-delivery-scope.md`. |
| Result         | **0 done, 1 partial, 22 not-started.** The wording "23 done" is not claimed for this project; the final matrix in Phase 6 reports the real count and names what was not exercised.                                                                                                                                       |

Test paths in future rows are relative to `server/` (Pest) or `app/` (Flutter). In Phase 0 no such path exists, so none is cited as evidence.

## Update rules

1. A status moves up only in the same change that adds the proof, and the Evidence cell names the file or test and the command that was run.
2. A claim of `done` needs a recorded run of the cited test or command on the commit it describes; a skipped or not-run test is reported as such.
3. An item whose proof needs an unreachable external system stays `partial` and keeps its `not exercised: <reason>` text.
4. Counts in the Result row are recomputed from the table whenever a status changes.
