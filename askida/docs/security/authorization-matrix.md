## 1. Principals

The spec fixes seven roles. One extra principal, `guest`, is added only to describe unauthenticated requests; it is not a role and never receives a token.

| Column    | Principal                   | How it is established                                                                                                                       | Notes                                                                                                               |
| --------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **guest** | no valid token or session   | no `Authorization` header, or an expired or revoked token                                                                                   | Auth endpoints, the impact read and the payment web endpoints only.                                                 |
| **donor** | `users.kind = donor`        | Sanctum token with ability `donor`, issued per device on login                                                                              | Pays for items and reads its own donations. Cannot own or join a shop.                                              |
| **owner** | `shop_members.role = owner` | Sanctum token with ability `merchant`, plus a `shop_members` row with role `owner` for the shop in the path                                 | Everything a merchant does for its own shop, including catalog, documents and payouts.                              |
| **staff** | `shop_members.role = staff` | Sanctum token with ability `merchant`, plus a `shop_members` row with role `staff` for the shop in the path                                 | Redeem a code and view redemptions for that shop. Nothing else: no catalog, no shop edit, no payouts, no documents. |
| **anon**  | `anon_devices.anon_id`      | Sanctum token with ability `anon`, issued by `POST anon/attest` after a device attestation verdict; the token carries exactly one `anon_id` | Reserve a code and delete its own device record. No `users` row exists for a recipient.                             |
| **mod**   | `moderator` (admin panel)   | `spatie/laravel-permission` role on an admin user, TOTP enforced at login                                                                   | Admin panel only. Shop verification, document review, abuse handling. No JSON API surface.                          |
| **fin**   | `finance` (admin panel)     | same mechanism as `mod`                                                                                                                     | Admin panel only. Payouts, reconciliation, payout holds.                                                            |
| **admin** | `admin` (admin panel)       | same mechanism as `mod`                                                                                                                     | Admin panel only. Role management and everything `mod` and `fin` can do, minus the prohibitions in section 4.       |

Rules that apply to every row:

- **Token abilities mirror roles** (spec section 6 item 3). `donor`, `merchant` and `anon` are mutually exclusive on one token. The shop-level distinction between `owner` and `staff` is never carried in the token: it is read from `shop_members` on every request, so a removed staff member loses access on the next call.
- **Admin roles never travel on the mobile API.** The `mod`, `fin` and `admin` columns do not appear in section 3 because no `/api/v1` endpoint accepts an admin identity. Admin access is Filament only (section 4).
- **Deactivated users** (`users.deactivated_at` not null) and **banned devices** (`anon_devices.banned_at` not null) are rejected on every request, checked in the database and not from token claims.
- **A user has one kind.** A merchant account cannot donate and a donor account cannot own a shop. This removes the "merchant pays itself" path at the identity level (see `threat-model.md`, merchant self-redeem collusion).

## 2. Denial convention

| Situation                                                                    | Status  | Problem `code`      | Rationale                                                                                           |
| ---------------------------------------------------------------------------- | ------- | ------------------- | --------------------------------------------------------------------------------------------------- |
| No token, expired token, revoked token                                       | 401     | `unauthenticated`   | Standard.                                                                                           |
| Valid token whose ability or kind cannot use the endpoint at all             | 403     | `forbidden_ability` | Decided before any database lookup, so it leaks nothing about the target.                           |
| Valid ability, target resource exists but is outside the actor's scope       | 404     | `not_found`         | A non-member shop, another donor's donation and another anon's hook look identical to a missing id. |
| Valid ability and scope, state forbids the action (for example expired code) | 409/422 | endpoint specific   | Defined per endpoint in the Phase 1 and Phase 2 contract; never reveals recipient data.             |
| Rate limit                                                                   | 429     | `rate_limited`      | `Retry-After` always present (spec section 6 item 5).                                               |

Response bodies are RFC 9457 problem details with `{type,title,status,code,request_id}` only (spec section 6 item 13).

## 3. Endpoint matrix (`/api/v1`)

Cell vocabulary: `Y` allowed, `-` denied (403 by ability, 401 for guest), `own` allowed only on the actor's own resource, `member` allowed only when a `shop_members` row of the stated role exists for the shop in the path.

### 3.6 Payment web endpoints (not token-authenticated)

These routes are reached by the in-app WebView and by the payment provider, not by the mobile API client. Their credential is a bound, single-use value, not a Sanctum token.

| Method   | Path              | Caller           | Credential                                                                     | Rule                                                                                                                                                                                                                          |
| -------- | ----------------- | ---------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET/POST | `pay/{token}`     | WebView (guest)  | opaque token bound to one `donations` row, expiring, single use                | Renders the provider checkout form for that donation only. Unknown, expired or used token is 404. The page contains no user-supplied content (spec section 6 item 16). `noindex`.                                             |
| POST     | `pay/callback`    | browser redirect | provider token in the payload                                                  | Never trusts a posted status or amount: always calls the provider `retrieve` API and only then transitions the donation (spec section 6 item 17).                                                                             |
| POST     | `webhooks/iyzico` | provider         | signature over the raw body, verified per the provider's current specification | Reject on missing or invalid signature or a stale timestamp. Idempotent on `event_id` through the unique index on `payment_events`. Returns 200 fast, then a queued job re-fetches the payment and only then creates `hooks`. |

## 4. Admin panel (Filament, `/admin`, not JSON)

Spec section 6 item 18. All three roles require a completed TOTP login, a `strict` session and an activity-log entry for every login and model change. An optional IP allowlist is a switch, not a role.

Cell vocabulary: `Y` allowed, `-` denied.

| Operation                                   | mod | fin | admin | Notes                                                                                                          |
| ------------------------------------------- | --- | --- | ----- | -------------------------------------------------------------------------------------------------------------- |
| View verification queue and shop details    | Y   | -   | Y     | Tax number and IBAN shown masked.                                                                              |
| Approve or reject a shop                    | Y   | -   | Y     | Reason recorded in the activity log. Only this action makes a shop visible to donors and recipients.           |
| Open a shop document                        | Y   | -   | Y     | 5-minute signed URL created per click and logged. No permanent URL.                                            |
| Suspend a shop or hold new reservations     | Y   | Y   | Y     | Abuse tool. Does not touch money. Open question D-6.                                                           |
| Ban or unban an `anon_id`                   | Y   | -   | Y     | The panel shows `anon_id`, platform, attestation verdict and counters only. Nothing else exists (rule AN-3).   |
| View donations and payment events           | -   | Y   | Y     | Read-only. No recipient data exists on these rows.                                                             |
| View payouts and reconciliation results     | -   | Y   | Y     | Read-only mirror of provider data.                                                                             |
| Place or release an automatic payout hold   | -   | Y   | Y     | Triggered by redemption-rate anomaly thresholds (spec section 6 item 22). Each change is logged with a reason. |
| Trigger a refund or a manual reconciliation | -   | Y   | Y     | Goes through the `PaymentGateway` contract. Never edits `donations.status` directly.                           |
| Reveal a decrypted tax number or IBAN       | -   | Y   | Y     | Explicit action, logged. Draft decision D-5.                                                                   |
| Manage admin users and roles                | -   | -   | Y     | Role changes need a fresh TOTP prompt.                                                                         |
| View activity log                           | -   | -   | Y     | The log carries no PII (spec section 6 item 21).                                                               |
| Open the Horizon dashboard                  | -   | -   | Y     | Behind the same admin authentication.                                                                          |
| Edit a hook's status or code by hand        | -   | -   | -     | Not possible for anyone. Hook transitions happen only through reserve, redeem and the expiry job.              |
| Impersonate another user                    | -   | -   | -     | Disabled (spec section 6 item 18).                                                                             |
| Read any recipient identity                 | -   | -   | -     | None exists to read (rule AN-4).                                                                               |

## 5. Anonymity invariants (explicit rules)

These come from spec section 0 item 6 and section 12. Each becomes a negative test in Phase 1 or Phase 2 and each is re-checked in Phase 6.

| Rule | Statement                                                                                                                                                                                                                     | Will be proven by (planned)                                                                                       |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| AN-1 | No endpoint returns recipient identity to a donor. Donor-facing responses never contain `anon_id`, code, code hash, device attributes, coarse or precise location, or a redemption timestamp finer than the day.              | Response-shape tests over `donations`, `donations/{id}`, push payloads and the impact endpoint.                   |
| AN-2 | No endpoint returns recipient identity to a merchant (owner or staff). Merchant-facing responses (`redeem`, `redemptions`) never contain `anon_id`, reservation time, device attributes, a code or a hash.                    | Response-shape tests over `shops/{id}/redeem` and `shops/{id}/redemptions`, including the losing parallel calls.  |
| AN-3 | `anon_devices` and `anon_daily_counters` hold no personal data: no name, email, phone, advertising id, IP address or coordinates. Columns are limited to those listed in spec section 5.                                      | Schema test that fails when a column outside the allowed list is added.                                           |
| AN-4 | No admin role and no admin panel page can display a recipient identity, because none is stored. The ban tool works on `anon_id` only.                                                                                         | Panel page tests asserting the field set; the schema test of AN-3.                                                |
| AN-5 | No precise recipient location is stored. Recipient location ranks shops on the device (coarse by default) and, if sent at all, is only the `shops?near=` query value, which is not persisted and not written to request logs. | Log-sample test (spec item 14) and a database scan for coordinate columns outside `shops`.                        |
| AN-6 | Recipients never have accounts, profiles, ratings or history beyond 30 days of aggregate counters; `DELETE anon/me` removes the device row and counters at once.                                                              | Deletion test (spec item 21) and a retention job test for the 30-day counter window.                              |
| AN-7 | A donor push ("Askın alındı") carries no recipient detail and no timing detail beyond the donation it refers to.                                                                                                              | Push payload shape test with the fake transport.                                                                  |
| AN-8 | A recipient code is shown once, stored only as a keyed hash and is not recoverable by any role, including `admin`.                                                                                                            | Database dump scan for plaintext codes (spec item 11) and a test that no endpoint returns a code after `reserve`. |

Copy rule that supports these invariants: product text never labels recipients with stigmatizing terms; it says "askıdan al".
