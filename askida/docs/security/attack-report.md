## 1. Layout and method

- Entry file `server/tests/Security/AttackSuiteTest.php`: one `describe` per threat that checks the suite itself. Each threat file must exist, name its register entry (which must still exist in `threat-model.md`), hold at least two tests, assert the refusal (status and problem `code` on the API, status on web pages and the object store), carry a negative control, and contain no sleep call, no empty `catch` and no skip. A last test refuses attack files outside the numbered list. This keeps the suite from shrinking or turning falsely green unnoticed.
- Threat files `server/tests/Security/Attack/ThreatNN<Name>Test.php`. The number is the register number. The files carry a `Threat` prefix because Pest builds a PHP class name from the file name and a class name cannot start with a digit.
- `Attack/AttackKit.php`: request helpers and `assertProblem(response, status, code)`, which checks the status, the `application/problem+json` media type, the `code` and the `status` member together.
- Concurrency: `tests/Security/Concurrency/ConcurrencyHarness.php` (existing) runs a pool of worker processes, each with its own database session. All of them wait on a PostgreSQL advisory lock and start together. The worker has a new `http` scenario: it sends one request through the HTTP kernel of its process, so routing, Sanctum, form requests, limiters and controllers all run, not only the engine call. No sleep decides an outcome; the only pause is the harness polling `pg_locks` until every participant waits at the barrier.
- Rate limits are tested against their production values (30 redeems a minute, 3 attestations a day, 60 reserves an hour per address, 10 presigns a day, 5 sign-ins a minute) with the limiter state itself. Windows are crossed by moving the test clock, never by sleeping.
- What the concurrency tests prove, and what they do not: the database guards (row locks, conditional updates, unique indexes, counter rows) hold when separate processes with separate PostgreSQL sessions hit the same rows at the same instant. Each worker process has its own in-memory (`array`) cache, so a rate limiter is never shared between workers; the parallel tests make no claim about limiter enforcement across processes or about the Redis limiter store. Limiters are tested in a single process (one limiter store), at their production values.
- Every attack sits next to its negative control: the same request made legitimately succeeds, so a refusal cannot come from a broken fixture.
- Assertions cover state, not only status codes: rows in `hooks`, `donations`, `payment_events`, `payment_mismatches`, `abuse_flags`, `anon_daily_counters`, `personal_access_tokens`, queued jobs and mails, objects in the bucket.

## 4. Findings and fixes

| #   | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | Severity            | Status                                                                                              |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- | --------------------------------------------------------------------------------------------------- |
| F1  | **Redeem limiter bypass by letter case.** The `redeem` limiter keyed its bucket by the raw `{shop}` path segment. The router (`whereUuid`) and PostgreSQL accept a UUID in any letter case, so a shop member could open a fresh 30-a-minute bucket per spelling of the shop id (up to 2^n spellings for n hex letters) and multiply the guess rate of threat 4.1. Red run: `Threat01…` "does not open a new limiter bucket…" got 200 (the right code redeemed after 30 guesses) instead of 429. | Medium              | Fixed: the key is lower-cased (`app/Providers/AnonServiceProvider.php`). Test green after the fix.  |
| F2  | **Presign quota bypass by letter case.** Same pattern in the `document-presign` limiter (`{id}` raw), so the owner could exceed 10 presigns a day per shop. Red run: `Threat14…` "stops the 11th presign…" got 409 (the request passed the quota and reached the document count check) instead of 429.                                                                                                                                                                                          | Low                 | Fixed: the key is lower-cased (`app/Providers/ShopsServiceProvider.php`). Test green after the fix. |
| F3  | **Host header reflected in the account deletion form.** `resources/views/web/account-deletion.blade.php` builds the form action with `route()`, which is absolute and takes the request host: `curl -H 'Host: evil.example' …/hesap-silme` renders `action="http://evil.example/hesap-silme"`. Not exploitable as found: the page is not in the page cache (it sets the session cookie), a browser cannot send a foreign `Host` cross-site, and the public CSP has `form-action 'self'`.        | Info                | Open: one-line view change (`route(..., absolute: false)`) belongs to the views owner.              |
| F4  | The existing `tests/Feature/Documents/DocumentUrlSignerTest.php` expiry case moves the test clock back, which makes the SDK sign a negative `X-Amz-Expires`; MinIO answers 400 `AuthorizationQueryParametersError`, not an expiry refusal, and the test accepts any 4xx. The attack suite signs a five-minute URL with a start time six minutes in the past instead and asserts 403 `AccessDenied`.                                                                                             | Info (test quality) | Covered here; the feature test is left as it is (not owned).                                        |

No other attack succeeded. Controls proven only at their documented strength (residual risks of the register stay as written): one PostgreSQL instance (no replica, no pooler), fake attestation verdicts, fake payment gateway with the real webhook verifier.

## 7. Not exercised

- Real provider verdicts (Play Integrity, DeviceCheck) and device farms: not exercised: no provider account, no devices (ADR-0006).
- Real payment provider (signature scheme as documented, sandbox calls): not exercised: no provider account; the real verifier runs with a run-time key.
- PostgreSQL replication or a pooler in transaction mode under the race tests: not exercised: one database instance.
- Behaviour behind the production edge proxy (Caddy) and the hosted object store: not exercised: no deployment.
- iOS: not exercised: no macOS.
